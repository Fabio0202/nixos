# NixOS 26.05 Upgrade — Investigation Notes

Context: bumped `nixos-25.11` → `nixos-26.05`, `home-manager/release-25.11` → `release-26.05`, and `stateVersion` to `"26.05"` across the flake + all host configs. The bump triggered several breakages; two of them (Hyprland + Neovim) stomped user config and need verification.

## ✅ Already fixed in code

### 1. Hyprland `hyprland.lua` Lua parse error
- **Symptom:** `unexpected symbol near '/' (line 10)` in `~/.config/hypr/hyprland.lua`.
- **Cause:** HM 26.05 added a `wayland.windowManager.hyprland.configType` option. Its default is decided via `lib.hm.deprecations.mkStateVersionOptionDefault { since = "26.05"; legacy.value = "hyprlang"; current.value = "lua"; }` — so with `stateVersion = "26.05"` it now defaults to `"lua"`. HM then writes `~/.config/hypr/hyprland.lua` (instead of `hyprland.conf`) and treats `extraConfig` as **Lua code**. Our `extraConfig` contains hyprlang `source = ~/.config/hypr/hyprland-stow.conf` — the `=` and `/` characters cause the parse error.
- **Fix applied:** `home/modules/hyprland/config/default.nix` — explicitly set `configType = "hyprlang";` to force the legacy `.conf`-writing behavior.
- **Why NOT migrated to Lua:** Your config is spread across ~10 stow'd hyprlang `.conf` files (`animations.conf`, `keybinds.conf`, `window-rules.conf`, DMS configs, etc.). Hyprland's new `hl.*` Lua API (`hl.on`, `hl.bind`, `hl.dsp.*`, settings-as-attrsets) has no clean 1:1 mapping for many hyprlang directives. A blind rewrite would risk subtle breakage. Better to migrate gradually, file-by-file, not in one shot.
- **Verified:** `home.file` now contains `hyprland.conf` (not `.lua`) after evaluation. ✅

### 2. Neovim `init.lua` stomp
- **Symptom:** `~/.config/nvim/init.lua` symlink replaced by a HM-written file (stow'd original moved to `init.lua.backup`), so the real nvim config stopped loading.
- **Cause:** HM 26.05's `programs.neovim` renamed `extraLuaConfig` → `initLua` and now **always writes** `~/.config/nvim/init.lua` with provider-disable Lua, unless `sideloadInitLua = true` (which injects the same Lua via `--cmd` flag instead). Since HM 26.05's neovim plugin type also now defaults to `"lua"` for `stateVersion >= 26.05`, the module writes an init file even though we never asked for one.
- **Fix applied:** `home/common-server.nix` — added `sideloadInitLua = true;` to the `programs.neovim` block.
- **⚠️ Unverified quirk:** Even with `sideloadInitLua = true`, `nix eval` still shows `/home/simon/.config/nvim/init.lua` in `home.file`. Per the module source line 626 (`enable = !cfg.sideloadInitLua;`) it should NOT be written when sideloaded. This needs investigation — possibly my eval was stale, OR another module (custom one?) is also writing it. **See "To verify tomorrow" below.**
